## P2 — 可改进

### R4-1: `read_http_request` 无 header 大小上限，可被超大 header OOM

**文件**: `src/http_mitm.rs:205-249`
**严重性**: P2

`read_http_request` 在读取 header 阶段不断 `buf.extend_from_slice`，无上限。恶意客户端发送超长 header（如 1GB 的 header 行）可导致内存耗尽。

**实际影响**: 低。代理监听在 127.0.0.1，只接受 iptables REDIRECT 的本地连接，外部无法直接访问。但本地恶意进程仍可利用。

**建议修复**: 在 header 读取循环中加 `if buf.len() > 65536 { return Err(...) }` 限制最大 header 大小。

### R4-2: `stream_http_response` / `stream_response_simple` header 读取无大小上限

**文件**: `src/http_mitm.rs:260-282, 402-425`
**严重性**: P2

与 R4-1 类似，响应 header 读取循环也无上限。恶意上游可发送超大响应 header。

**实际影响**: 低。上游连接是 TLS 验证后的可信 AI API。

**建议修复**: 同 R4-1，加 65536 字节上限。

### R4-3: `has_chunked_terminator` 可能误匹配 chunk data 中的 `\r\n0\r\n\r\n`

**文件**: `src/http_mitm.rs:489-494`
**严重性**: P2

```rust
fn has_chunked_terminator(buf: &[u8]) -> bool {
    if buf.starts_with(b"0\r\n\r\n") {
        return true;
    }
    buf.windows(7).any(|w| w == b"\r\n0\r\n\r\n")
}
```

**问题**: 如果 chunk data 中恰好包含 `\r\n0\r\n\r\n` 这 7 字节序列，会误判为 chunked 终止。这在二进制响应体（如 base64 编码的图片数据）中概率不为零。

**实际影响**: 极低。AI API 响应通常是 JSON 文本，几乎不可能在 body 数据中出现精确的 `\r\n0\r\n\r\n` 序列。即使误匹配，最坏结果是提前结束 body 读取（client 收到的数据已完整转发，只是 upstream 连接可能被提前关闭）。

**权衡**: 之前的 `find_chunked_end` 做完整 chunk 解析，更精确但要求完整 body 在内存中（R3-4 已修复为滑窗）。当前 `has_chunked_terminator` 是精度与内存的权衡。64KB 滑窗进一步降低了误匹配概率（只有最后 64KB 在 buffer 中）。

**建议**: 当前可接受。如需更精确，可在滑窗中做完整的 chunk 边界解析，但复杂度显著增加。

### R4-4: `is_connection_close` 不处理逗号分隔的多个 Connection 值

**文件**: `src/http_mitm.rs:517-523`

```rust
l.splitn(2, ':').nth(1).map(|v| v.trim() == "close").unwrap_or(false)
```

**问题**: HTTP `Connection` header 可包含多个逗号分隔的值，如 `Connection: keep-alive, close`。当前代码只做 `trim() == "close"` 精确匹配，不匹配 `keep-alive, close`。

**实际影响**: 极低。AI API 响应极少使用逗号分隔的 Connection 值。且 `close` 通常是唯一值。

**建议修复**: 改为 `v.split(',').any(|t| t.trim() == "close")`。

## P3 — 风格 / 小改进

### R4-5: `stream_http_response` 的 response audit event 大量空字段

**文件**: `src/http_mitm.rs:362-388`

响应审计事件中 `agent_id`, `session_id`, `app_name`, `method`, `host`, `port`, `path`, `model` 等全是空字符串/0。这些信息在请求审计事件中已记录，响应事件只记录 `request_id` 关联。

**评估**: 这是设计选择，不是缺陷。通过 `request_id` 关联请求和响应，响应事件不需要重复请求字段。JSONL 中两条记录（request + response）通过 `request_id` 关联。

包括 `type_complexity`（2个）、`redundant closure`（4个）、`split_once` 建议（2个）等。不影响功能。

## 已确认无缺陷的领域

- **TLS 握手**: `extract_sni` 边界检查完整，`handle_tls_mitm` 有 10s 超时
- **SO_ORIGINAL_DST**: `get_original_dst` 正确处理 IPv4/IPv6
- **CA 证书**: `load_or_generate` 正确处理加载/生成两种路径，权限设为 0o600
- **cert cache**: FIFO 淘汰，1000 上限，`RwLock` 读写分离
- **audit writer thread**: `sync_channel(1000)` + `try_send` 非阻塞，`flush()` 有 5s 超时
- **attribution**: `/proc/net/tcp` 解析正确，父进程链遍历有环检测（`visited` HashSet）
- **graceful shutdown**: `SIGTERM`/`SIGINT` → `abort()` accept loop → `flush()` 审计
- **keep-alive**: request→response 严格顺序，`Connection: close` 双向检测
- **chunked 滑窗**: 64KB `tail_buf` + `has_chunked_terminator`，大文件下载不再 OOM
- **整数溢出**: `find_chunked_end` 用 `checked_add`
