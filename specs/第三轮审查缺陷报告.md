## P1 — 应修复

### R3-2: `is_chunked` / `is_connection_close` 用 substring 匹配，可能误匹配 header 值

**文件**: `src/http_mitm.rs:487-493`
**严重性**: P1

```rust
fn is_chunked(header_str: &str) -> bool {
    header_str.to_lowercase().contains("transfer-encoding: chunked")
}
fn is_connection_close(header_str: &str) -> bool {
    header_str.to_lowercase().contains("connection: close")
}
```

**问题**: `contains` 在整个 header 字符串中搜索，不限于行首。如果某个 header **值**中包含 `transfer-encoding: chunked`（如 `X-Debug: transfer-encoding: chunked`），会误判为 chunked。同理 `connection: close` 可能在 `Set-Cookie` 或自定义 header 值中出现。

**实际影响**: 低。HTTP 请求/响应头中值包含这些子串的场景极少。但这是一个正确性缺陷。

**建议修复**: 改为逐行匹配，只检查以 `transfer-encoding:` 或 `connection:` 开头的行。

### R3-3: `parse_content_length` 硬编码 `line[15..]` 偏移，脆弱

**文件**: `src/http_mitm.rs:477-485`

```rust
fn parse_content_length(header_str: &str) -> Option<usize> {
    for line in header_str.lines() {
        if line.to_lowercase().starts_with("content-length:") {
            let val = line[15..].trim();  // "content-length:" = 15 chars
            return val.parse().ok();
        }
    }
    None
}
```

**问题**: `line[15..]` 用字节偏移截取。`"content-length:"` 确实是 15 字节，但 `to_lowercase()` 产生的新 String 和原 `line` 的长度关系依赖于 ASCII。如果 header name 含非 ASCII 字节（HTTP 标准不允许，但恶意输入可能），`line[15..]` 可能 panic（非 char boundary）。

**实际影响**: 极低。HTTP header name 按 RFC 7230 只允许 ASCII token 字符。但恶意构造的请求可能导致 panic。

**建议修复**: 用 `line.splitn(2, ':').nth(1)` 替代硬编码偏移。

### R3-4: `stream_response_simple` 对大 chunked 响应无界累积 `body_buf`

**文件**: `src/http_mitm.rs:432-464`

```rust
let mut body_buf = if is_chunked {
    let mut v = Vec::new();
    v.extend_from_slice(body_start);
    v
} else {
    Vec::new()
};
// ...
loop {
    // ...
    if is_chunked {
        body_buf.extend_from_slice(&tmp[..n]);
    }
}
```

**问题**: 非 AI 请求的 chunked 响应会在 `body_buf` 中累积**整个响应体**直到检测到 `0\r\n\r\n`。对于大文件下载（如 100MB 的非 AI 响应），这会消耗大量内存。

`stream_http_response`（AI 请求）有同样的问题——`body_buf` 也累积整个 chunked body。

**实际影响**: 中。非 AI 主机走 blind_tunnel 不经过此函数，但 AI 主机上的非 AI 路径请求（如静态资源）会经过。大文件下载可能 OOM。

**建议修复**: 不需要累积整个 body。改为滑动窗口：只保留最后 N 字节用于检测 `0\r\n\r\n`。或在每次 read 后检查最后几个字节是否包含 chunked terminator。

### R3-5: `find_chunked_end` 在 chunk size 行超长时无限制

**文件**: `src/http_mitm.rs:497-524`

```rust
fn find_chunked_end(buf: &[u8], start: usize) -> Option<usize> {
    let mut pos = start;
    loop {
        let line_end = buf[pos..].windows(2).position(|w| w == b"\r\n")?;
        let size_str = std::str::from_utf8(&buf[pos..line_end_abs]).ok()?;
        let chunk_size = usize::from_str_radix(...).ok()?;
        pos = line_end_abs + 2;
        if chunk_size == 0 { ... }
        pos += chunk_size + 2;
        if pos > buf.len() { return None; }
    }
}
```

**问题**: 如果 `chunk_size` 被恶意设为 `usize::MAX`，`pos += chunk_size + 2` 会溢出（debug 模式 panic，release 模式 wraparound）。wraparound 后 `pos` 可能小于 `buf.len()`，导致后续 `buf[pos..]` 读到错误位置甚至 panic。

**实际影响**: 低（需要恶意上游），但这是一个安全相关缺陷。

**建议修复**: 用 `pos.checked_add(chunk_size + 2)` 替代 `pos += chunk_size + 2`。

### R3-6: `blind_tunnel` 两个方向超时 error message 相同

**文件**: `src/proxy.rs:203, 217`

```rust
.map_err(|_| -> BoxError { "blind tunnel idle timeout".into() })??;  // line 203
.map_err(|_| -> BoxError { "blind tunnel idle timeout".into() })??;  // line 217
```

**问题**: 两个方向（client→upstream 和 upstream→client）的 error message 相同，日志中无法区分是哪个方向超时。

**建议修复**: 改为 `"blind tunnel idle timeout (client→upstream)"` 和 `"blind tunnel idle timeout (upstream→client)"`。

### R3-7: `cleanup_old_events` 打开新连接，与 writer 线程并发写入

**文件**: `src/audit.rs:257-271`

```rust
pub fn cleanup_old_events(db_path: &Path) -> Result<(), String> {
    let conn = Connection::open(db_path).map_err(|e| format!("open: {e}"))?;
    // DELETE ...
}
```

**问题**: `cleanup_old_events` 每 10 分钟在 main.rs 中被调用（第 84-89 行），打开一个新 SQLite 连接执行 DELETE。同时 writer 线程持有另一个连接持续 INSERT。SQLite WAL 模式支持并发读写，但新连接没有设置 `PRAGMA journal_mode=WAL`，可能退化到默认 journal 模式导致锁冲突。

**实际影响**: 低。WAL 模式是数据库级别的持久化设置，新连接会继承。但如果数据库被删除重建（如测试），新连接可能不在 WAL 模式。

**建议修复**: 在 `cleanup_old_events` 中也设置 `PRAGMA journal_mode=WAL`。

### R3-8: `ca.rs generate_leaf` 每次调用都 `self.ca_params.clone()`

**文件**: `src/ca.rs:112-115`

```rust
pub fn generate_leaf(&self, hostname: &str) -> Result<...> {
    let ca_cert = self.ca_params.clone().self_signed(&self.ca_key)
        .map_err(|e| format!("ca self_signed: {e}"))?;
```

**问题**: `CertificateParams::clone()` 复制整个 CA 参数结构体。每次叶子证书生成都克隆一次。对于高频请求（如缓存未命中时），这是不必要的开销。

**实际影响**: 低。CertCache 有 1000 条 FIFO 缓存，命中率应很高。每次 clone 只是参数结构体，不涉及密钥。

**建议**: 当前可接受。如果未来性能成为瓶颈，可改为 `Arc<CertificateParams>` 共享。

### R3-9: `attribution.rs lookup_peer` 中 `read_env_vars(pid)` 读取的是 direct_pid 而非 agent_pid

**文件**: `src/attribution.rs:79`

```rust
let (mut app_name, mut agent_id, mut session_id) = read_env_vars(pid);
```

**问题**: `pid` 是直接持有 socket 的进程 PID（可能是 curl/python3 等工具进程），而 `agent_pid` 是通过父进程链解析出的真正 agent 进程。环境变量 `AGENTGATEWAY_*` 应该从 agent 进程读取，而非工具进程。

**实际影响**: 中。如果 agent 通过 curl 发起请求，curl 不会继承 agent 的 `AGENTGATEWAY_*` 环境变量（除非 agent 显式设置），导致 app_name/agent_id/session_id 为空，回退到 exe basename。

**建议修复**: 改为 `read_env_vars(agent_pid.unwrap_or(pid))`。

### R3-10: `find_socket_inode` 在 `parts[1].split(':').nth(1)?` 时使用 `?` 可能误跳

**文件**: `src/attribution.rs:130-132`

```rust
let local_port = u16::from_str_radix(
    parts[1].split(':').nth(1)?, 16
).ok()?;
```

**问题**: 如果 `/proc/net/tcp` 中某行的 local address 格式异常（无 `:`），`nth(1)?` 返回 `None`，`?` 会从整个函数提前返回，跳过后续所有行。

**实际影响**: 极低。`/proc/net/tcp` 格式由内核保证。但防御性编程应改为 `continue`。

**建议修复**: 改为 `match` + `continue` on `None`。
